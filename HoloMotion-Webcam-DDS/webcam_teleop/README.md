# 摄像头实时模仿（本机原型）

流程：浏览器 MediaPipe Pose → 33 个三维人体关键点 → Mink/DAQP IK 映射 G1 参考姿态 → 官方 HoloMotion v2.0.0 ONNX 策略 → PD 控制 → MuJoCo。

**当前支持站立时的手臂、肘部与小幅躯干跟随。根部和腿部参考保持站姿，不支持走动、跳跃、深蹲、手指或精确全身动作捕捉。** 这是新增的摄像头适配原型，不是 HoloMotion 官方 VR 接口，也没有使用官方 HoloRetarget 人体模型流水线。

## 在 VS Code 使用

本文件夹应在左下角显示 `WSL: Ubuntu-24.04`。

1. 按 `Ctrl+Shift+B` 运行“启动纯 MuJoCo 调试（8766）”；或者在项目根目录的 WSL 终端执行：

   ```bash
   bash webcam_teleop/start_sim.sh
   ```

2. 用 **Windows 端 Edge 或 Chrome** 打开 <http://localhost:8766>（纯 MuJoCo）。
   <http://localhost:8765> 是单独的实机遥操服务；页面顶部提供两个入口。
3. 点击“开启摄像头”，自行允许浏览器摄像头权限。画面中要能看见肩、双肘、手腕和髋部。
4. 纯仿真点击“校准站姿”。G1RA 实机模式选择舒适且可达的姿态，点击“采集并对齐机器人（会运动）”；启动对齐后可自行点击“开始跟随”，不再要求通过到位误差门槛。
5. 缓慢抬臂、伸臂、弯肘或轻微倾斜躯干。绿色点为映射参考，灰色机器人受预训练模型控制。
6. 点击“暂停仿真”暂停控制；“关闭摄像头”停止采集。跌倒后点击“机器人复位”，再校准。

关键点可见度不足或超过 0.5 秒未收到数据时，不继续推进仿真。恢复有效数据后会继续；点击暂停则需要重新点击开始。页面关闭会请求暂停，采集自动停止；服务还会以数据过期保护作为后备。

停止服务：在运行服务的终端按 `Ctrl+C`。当前由安装过程启动的服务可以关闭 WSL 后再用上述命令自行启动；不要在有其他 WSL 工作时随意关闭整个 WSL。

### 纯 MuJoCo 动作路径调试

`8766` 的链路为摄像头骨架 → IK 参考 → HoloMotion → 模型 PD → MuJoCo 物理 →
本地状态反馈。它不创建 G1RA 或 DDS 传输，不访问机器人位姿接口；不要求机器人在线、
实机对齐或实机反馈，也没有机器人桥的 0.02 rad 指令步长、锁腰或 arm_sdk 门限。
开启摄像头、完整入镜后会自动校准，可直接点击“开始跟随”；也可手动重新校准。
跌倒后点击“机器人复位”。

保留模型本身的关节/力矩范围、IK 映射限幅和人体关键点有效性检查，因此是模型中
可实现动作的调试环境，并非解除所有约束。默认使用 ONNX 原增益和 MuJoCo 重力。
映射参数可通过 `--retarget-config /path/to/debug.yaml` 单独加载，不必改实机配置。

启动器默认优先项目 `.venv`，其次当前用户的 `~/HoloMotion-Webcam-Source/.venv`，
也可用 `HOLOMOTION_PYTHON=/path/to/python` 指定。纯仿真允许 CPU 推理；界面显示
实际控制频率。`HOLOMOTION_SIM_PORT` 可改端口，默认 8766。
兼容入口 `bash webcam_teleop/start.sh` 也启动这个纯仿真服务。
即使命令行传入其他 backend，纯仿真启动器最后也会固定为 direct。

## 文件

### 实机从当前姿态开始

G1RA 接管必须收到 0.5 秒内的有效状态。接管时清空策略 KV、观测历史与步号，
用实测关节角、关节速度及 IMU 更新模型状态，第一条指令保持当前关节角。
第一帧参考也使用当前关节角，此后参考按映射限速逐步靠近人体目标。
实机指令每个策略周期最多变化 0.02 rad；下肢锁定在本次接管的实测角。

每次推理前刷新实机反馈；暂停后重新开始会重新取实测起点。
无效或过期反馈会阻止接管，不再回退发送默认站姿；页面复位也不会发送实机站姿。
G1RA 校准改为冻结人体姿态并缓慢对齐实机，不再要求人先摆成模型默认站姿。

对齐只调整双臂 8 个肩肘关节，其余关节目标保持点击时的实测角。
速度上限为 0.25 rad/s（每周期最多 0.005 rad）。实测角最大误差不超过
0.05 rad、实测速度不超过 0.08 rad/s，并在持续更新的反馈中保持至少 0.6 秒，
会记录为“观察到静止”；这些数值仅供诊断，不再限制开始跟随，也不宣称达到现场精度。
机器人当前运行 `g1_remote_action.arm_backend`（`rt/arm_sdk`），启动网页服务时必须指定
`--g1ra-control-mode arm_sdk`。此时状态码 3/4 分别表示手臂动作流跟随/保持，均可进行对齐，
不要求退出官方运控或进入全身低层 POLICY。腿和平衡仍由官方运控负责；腰由机器人桥锁定。

只有使用全身 `sdk_backend` 时，才采用 `--g1ra-control-mode full_body`（兼容默认值），
并要求进入其 POLICY 状态。两种桥在当前协议中复用状态码，不能仅凭 3/4 自动识别接口。
程序不自行切换机器人模式。已取消 45 秒到位超时；反馈过期或接口未就绪/急停仍会停止对齐。
也可设置 `HOLOMOTION_G1RA_CONTROL_MODE=arm_sdk`；本机当前服务显式使用该配置。

对齐期间持续靠近并保持冻结目标，不自动开始跟随；用户可在对齐中手动开始，无需等待到位。
重新点击会重新采集绝对目标，
不累加关节偏移；点击暂停、关闭实机开关、换摄像头或复位会取消对齐。
冻结目标对齐期间不要求人体每一帧都有效；关闭摄像头或离开页面会发送暂停请求，
机器人侧仍保留断流保护。可见的 MuJoCo 灰色姿态使用实测反馈。

开始跟随后才启用 HoloMotion 策略。对齐阶段不运行策略，仅使用现有 IK 和桥的 PD；
本次没有调整实机 kp/kd，也没有加入额外前馈力矩。

后台以 1 Hz 异步记录关节诊断数据，默认 WSL 路径为 `/tmp/holomotion-motion-8765.jsonl`，
可用 `HOLOMOTION_MOTION_LOG` 改路径。记录含关节名、原始弧度单位的参考/冻结目标、
下发角、实测角和速度、状态序号与年龄、对齐最大误差及是否观察到静止。
日志单文件最多约 25 MiB，保留两份轮转备份；队列满时记录丢弃计数，不阻塞控制线程。
不记录摄像头图像。诊断结果不作为到位门槛，原有反馈有效性、急停和指令限速仍生效。

这项改动对齐起点并限制目标跳变，不会将人体当前姿态永久设为机器人零位，
也不能保证策略在任意机器人姿态下都稳定。基座位置/线速度没有实测来源，
不会把仿真残留线速度当成机器人实测速度。实物表现需现场验证。

- `server.py`：本机 HTTP 接口、HoloMotion 模型、MuJoCo 50 Hz 控制、独立画面线程。
- `retarget.py`：校准、手臂几何目标、Mink 调用、参考平滑与速度限制。
- `mink_ik.py`：Mink/DAQP 肘腕位置任务、硬关节限位和固定分支恢复。
- `web/app.js`：摄像头与控制面板。
- `web/pose-worker.js`：独立 Worker 中执行 MediaPipe，避免识别阻塞页面。
- `web/vendor/`：固定下载的 MediaPipe 1.1.1、WASM 和 pose_landmarker_lite 模型；本地运行不依赖在线 CDN。
- `.vscode/tasks.json`：VS Code 启动任务。

## 数据与模型

### 固定的 Mink IK 后端

WSL 运行环境安装 `python -m pip install -r webcam_teleop/requirements-ik.txt`。
固定 Mink 1.3.0、qpsolvers 4.13.0、DAQP 0.10.3；当前验证环境为 MuJoCo 3.17.0。
上游为 <https://github.com/kevinzakka/mink>。缺少依赖时启动报错，不悄悄回退到旧 DLS。

骨架输入、比例映射、One Euro 滤波和 HoloMotion 策略保留。仅双臂 8 个肩肘关节参与求解，
根部、腿、腰和腕在 IK 中严格冻结；腰仍由外部原有躯干映射决定。手掌朝向不作为输入。
Mink 使用独立模型副本和 MjData，不修改物理仿真模型或实机反馈数据。

关节限位及 0.02 rad 余量作为 QP 约束，而不是先求解再截断。内部每次迭代仍限制步长，
最终参考仍使用原有平滑和 2.5 rad/s 速度限制；实机桥限速、PD 和重力前馈没有改变。
`mapping.ik_continuity_weight` 现在是 Mink PostureTask 残差权重，与旧 DLS 系数不可直接等同。

Mink 仍是局部求解器。肘/腕位置残差超过 `ik_recovery_error_m`（默认 3 cm）时，
只对误差较大的手臂尝试三个固定种子（肘上、肘下、前伸），全部由 Mink 约束求解。
只有误差实质改善才换分支；相近精度时选择接近上一参考的解。最终输出继续限速。
`ik.last_diagnostics` 提供分支名、恢复次数和各肘腕位置残差；这不是全局最优保证。
当前未启用 Mink 避碰约束，不保证恢复过程或任意交叉姿态无碰撞。

回归脚本：`diagnostics/mink-ik-2026-11-06/validate_mink.py`，加 `--policy` 可做真实 ONNX
和 MuJoCo 离线验证；不创建机器人传输。服务 `/api/status` 的 `ik_solver` 为 `mink/daqp`，
可区分新服务与尚未重启的旧进程。实机链路必须另行现场验证。
跟随状态的 `ik` 字段及实机 1 Hz 诊断日志包含当前 IK 残差、分支和累计恢复次数。

### 视频骨架抖动处理

实时路径按新骨架的序号和浏览器采集时间戳更新，20 Hz 输入不会被50 Hz控制循环
重复当成新测量或重新求解 IK；控制循环仅平滑追踪最新接受的参考。
旧客户端未提供时间戳时使用服务端接收时间；换摄像头和重新校准清空跟踪历史。

处理顺序为：去除骨架全局平移 → 跳点/置信度短暂保持 → One Euro 自适应低通 →
带前一参考解连续性约束的 IK → 小变化保持 → 原有关节参考平滑和限速。
低可信数据最多保持 0.25 秒，连续三帧一致的新位置可恢复接受；持续无效输入仍暂停。
原始时间戳不前进的包不会刷新数据有效期。

参数集中在 `retarget_config.yaml` 的 `tracking` 段及 `mapping.ik_continuity_weight`：

- 默认 One Euro 最低截止频率 1 Hz，beta=3（坐标为米，采集时间为秒）。
- 参考角在约0.29°内稳定0.25秒后保持，偏离保持点约0.86°时恢复跟随。
- `tracking.enabled: 0` 可关闭输入滤波与小变化保持；连续性权重设0可关闭IK正则。
- 降低最低截止频率会更稳但更迟钝；提高 beta 会让运动时更跟手。
- 微小主动动作可能被保持区间吸收；必要时缩小保持阈值，而不是提高电机增益。

没有对 HoloMotion 最终动作施加强低通，也没有修改机器人侧 PD。视频叠加骨架仍为原始
识别结果，控制参考使用处理后的数据。修改参数需重启服务，不会自动提交代码或执行实机动作。

离线比较脚本为 `webcam_teleop/tests/benchmark_tracking.py`，与提交 `3cf849f` 对比：
在20 Hz、关键点标准差3 mm的两组静止合成输入下，8个肩肘参考角的变化率RMS分别下降
约98.95%和92.12%；慢速抬臂半程响应额外延迟约120 ms。
结果文件为 `diagnostics/jitter-filter-2026-11-05.json`，仅验证参考/IK链路，不代表策略输出或实机效果。

算法依据：[One Euro 作者说明](https://gery.casiez.net/1euro/)。

摄像头图像只在 Windows 浏览器中处理；仅 33 个关键点坐标发给本机 WSL 服务。不上传云端，不默认保存人体图像、视频或动作。服务仅监听本机回环地址。

HoloMotion 使用已经安装的 `checkpoints/HoloMotion_motion_tracking_model_v2.0.0/exported/model_10500.onnx`；复用官方观测拼接、缓存和 PD 控制器，不是直接把摄像头关节角设置成机器人实际姿态。

实时参考无法知道未来动作。当前模型的 1–5 帧未来目标使用当前平滑后的目标保持，因而与离线预知未来的动作跟踪不同。请避免快速动作。

## 验证范围

### PD 增益对比实验

当前摄像头服务的 MuJoCo 仿真默认使用 ONNX 模型原始 PD 增益。
设置 `HOLOMOTION_SIM_PD=bridge` 可对比 `g1-remote-action/config/bridge.yaml`
中的默认 PD 增益：手臂 kp=40、kd=3，腰 kp=200、kd=5，腿部按关节配置。
direct、DDS 仿真以及 g1ra 的纯仿真模式均生效；实机发送路径不受此开关影响。
重力保持原设置，启动日志打印实际重力向量与 PD 配置名称。

重启服务后，在页面保持“真机开关”关闭，再校准并开始跟随，观察静止时是否摆动。
这个实验只对比增益，不能视为完整复现真实硬件、控制频率或下肢锁定行为。

要恢复 ONNX 模型原增益，使用原启动命令并加环境变量，例如：

```bash
HOLOMOTION_SIM_PD=model bash webcam_teleop/start.sh
```

不设置该变量，或设置 `HOLOMOTION_SIM_PD=model`，则使用模型原增益。

- 已验证 MediaPipe 官方测试图能输出 33 个图像和三维世界关键点。
- 已用连续合成站姿 / 抬臂输入验证实际 HTTP → IK → HoloMotion GPU → MuJoCo 控制链路、站立稳定性、关节响应、乱序拒绝和 0.5 秒过期暂停。
- 真正使用本人的摄像头、光照、入镜范围与动作效果，仍需用户点击允许后现场验证。不能把合成输入测试称为真人实时模仿已经完成。

## 真人现场确认

用户已在 Windows 浏览器中打开本地摄像头，看到了自己和骨架关键点；在调整入镜范围、校准并开始跟随之后，明确确认“机器人能跟着抬臂”。因此，本机的真人摄像头 → 关键点 → 映射 → HoloMotion → MuJoCo 抬臂链路已经由用户现场确认。

这次确认限于站立上肢动作原型，未验证行走、跳跃、复杂全身运动或长时间运行效果。后续仍可根据实际跟随误差继续调整校准和映射。

## 机器人端重力前馈

G1RA 动作帧现带有对齐/策略跟随/保持阶段标记，机器人端分别计算完整重力或
Dex3 相对原橡胶手的重力差量。功能默认关闭，尚未实机验证；运行中的本机服务
需重启加载阶段标记。模型、参数、部署备份和验证结果见
[手臂重力前馈说明](../deployment/arm_gravity/README.md)。

## 画面来源与策略反馈来源

页面机器人面板提供两个独立选择：

- **画面来源**：实机接口位姿 / HoloMotion 本地仿真。随时可切换，只改变显示。
  实机来源优先使用 HTTP 位姿接口，也可使用新鲜的 G1RA 状态；过期时显示不可用，
  不会静默替换为仿真画面。本地仿真是独立 MjData 的实际物理推进。
- **策略反馈**：实机回传 / 本地 MuJoCo，仅实机服务提供，默认仍为实机回传。
  必须先暂停或停止对齐，切换后清空策略历史并关闭下发，需要重新采集并对齐。
  此选择影响后续动作，和显示选择互不联动。

选择本地反馈时：人体关键点 → IK 参考 → HoloMotion（读取本地物理状态）→
关节目标 → 实机与本地仿真。手臂限速后的实际目标也用于更新策略的上一动作历史。
每周期只做一次模型推理；实机位姿只在接管时用于
建立起点、对齐、监测和断流保护，后续不会覆盖本地仿真反馈。
即使使用本地反馈，实机断流/无效状态仍会停止下发。

本地物理使用现有 MuJoCo 模型及所选仿真 PD 配置，并保留重力。实机仍使用
机器人端的增益、Dex3 重力前馈、滤波和限位；这些差异不会被这个开关消除。
arm_sdk 模式下，仿真手臂吃本机已经限速的发送目标，仿真腿腰继续由 HoloMotion
维持平衡；实机腿腰则由官方控制/锁腰负责。因此它是本地闭环验证，不是实机的
精确数字孪生。跟随时仿真跌倒会暂停本地反馈控制。

关节诊断日志增加 `feedback_source` 和 `simulated_q_rad`，便于与实测角度对照。
API：`set_display_source` / `set_feedback_source`，参数 `source` 为 `robot` 或
`simulation`；`/api/status` 返回选择、画面可用性及 `local_simulation` 状态。
