# 待研发方案：摄像头骨架接入宇树官方遥操算法

日期：2026-11-05（Asia/Shanghai）  
状态：待研发，尚未实现或验证本方案  
当前决策：优先验证现有 HoloMotion 链路调整 kp、kd 后能否满足演示要求；本方案作为后续替代路线保留。

## 1. 目标与范围

利用现有浏览器摄像头和人体骨架，替代宇树官方遥操项目的 XR 位姿输入，复用其手臂 IK、重力补偿和手臂控制器，完成站立上肢模仿。

首期验证双臂抬起、前伸、侧举和弯肘。腕部采用约定朝向；手指、精确掌心旋转、腰部跟随、行走和全身动作不纳入首期。

下肢平衡拟交给官方运控，上肢采用官方支持的手臂接口。开发前必须核实目标机器型号、固件及运控模式是否支持该组合，不能沿用当前全身低层接管方式后假定官方运控仍在维持平衡。

## 2. 现状与动机

现有链路：

```text
MediaPipe 骨架 → 肩肘 IK 参考 → HoloMotion ONNX 策略
→ 全身关节目标 → 仿真 PD / G1RA 桥 → 执行
```

用户现场反馈：人体静止时实机手臂持续摆动。尚未通过同步记录确认摆动首次发生在参考、策略目标、最终下发目标还是电机执行阶段，根因未定。

已知实现差异包括实机与模型 PD 不一致、实机默认覆盖下肢目标、切换时策略历史未完整同步。gyro 写入基座角速度的遗漏已修补；旧进程不会自动加载该修改，实机运行效果尚待验证。

用户已观察到：将仿真全身 PD 换成桥默认值后机器人倒下。该现象不能单独归因为手臂增益，因为同次实验也改变了髋、膝、踝和腰的增益。

替代方案将去掉 HoloMotion 策略这一层，便于逐段检查目标生成和关节执行；最终稳定性仍需验证。

## 3. 拟采用的链路

```text
浏览器摄像头 / MediaPipe
  → 带序号、采集时间和置信度的骨架
  → 坐标校准、人体比例映射、滤波、工作空间限制
  → 左右手目标位姿；按需增加肘部目标
  → 宇树 G1_29_ArmIK：关节角 + 重力补偿力矩
  → 目标连续性检查、限速及必要的加速度限制
  → 宇树手臂控制器
  → 官方手臂接口 / 电机执行
  ← 实测关节角和速度
```

优先在机器人侧运行 IK 和控制器；浏览器/工作站只发送骨架或适配后的目标。具体计算部署位置由依赖、实测求解耗时和网络延迟决定。

不得同时运行两个控制同一组手臂电机的发布者。

## 4. 输入适配

### 4.1 骨架与坐标

复用肩、肘、腕、髋关键点及其置信度。原始摄像头坐标不能直接作为机器人目标坐标。

校准时建立躯干坐标系，确认前、左、上方向和左右手对应关系。以肩部为基准，使用人体上臂、前臂方向，结合机器人自身臂长和肩部位置构造目标；避免人体移动或比例差异将目标带出机器人工作空间。

适配器的输出必须声明坐标参考系、单位（米、弧度）、姿态表示、序号与原始采集时间。

### 4.2 手腕朝向

官方 `solve_ik()` 接受左右两个 4×4 目标变换，包含位置与朝向。当前肩肘腕位置链不能完整确定掌心朝向；虽然 MediaPipe 输出还包含其他点，现有映射没有使用它们估计手部朝向。

首期采用校准后的约定朝向，或调整朝向约束权重。固定末端朝向不等于固定三个腕关节角：肩肘移动时，腕部仍可能转动以保持末端朝向，需要验证关节活动范围。

后续可引入手部关键点估计朝向，或增加手部追踪模块。不得把估计不足的朝向当成精确测量。

### 4.3 肘部与多解

官方原始求解接口没有人体肘部目标，单靠末端位姿可能得到不同的肘部构型。

首期依靠实测角初始化、历史解和平滑约束检查连续性；若肘形不符合演示需求，增加肘部位置/方向代价。此项属于对官方 IK 的扩展。

手臂伸直或关键点近共线时，朝向构造容易不稳定，应保留连续的上一有效方向，避免坐标轴突然翻转。

## 5. 更新频率与时序

- 现有网页每 50 ms 尝试识别一次，上限约 20 Hz；识别忙时跳帧，实际有效频率需测量。
- 官方主循环默认 30 Hz，负责更新目标并求解 IK；这是配置目标，实际能否达到取决于求解耗时。
- 官方 G1 手臂发布线程周期为 1/250 s，目标约 250 Hz，使用最新关节目标持续发布，不要求摄像头达到 250 Hz。

初期可接收约 20 Hz 新骨架，目标更新循环按 30 Hz 调度，电机发布沿用官方 250 Hz 线程。没有新目标时可保持最近有效解；是否插值应由连续性测试决定，不能将重复帧计为新的观测。

仅保留最新目标，避免网络积压。追踪原始采集时间、接收时间及求解完成时间；单纯重发旧骨架不能延长有效期。两台机器的时钟不可直接相减，跨机时间需要同步或明确换算。

骨架丢失、低置信度、目标过期或 IK 失败时，应进入明确的手臂保持/退出状态。超时阈值和退出行为需要在仿真与目标接口验证后定案，不能无限持续执行旧目标。

记录实际骨架频率、IK 耗时分布、发布间隔、数据年龄、失败率与限速触发次数。

## 6. 模型、PD 与前馈

官方 G1 遥操的肩肘 PD 为预设 kp=80、kd=3，腕部 kp=40、kd=1.5。其求解器另用 `pin.rnea()` 在零速度、零加速度条件下计算重力补偿力矩，并将其写入电机 tau 字段。

这些增益不是 IK 按动作时长计算的。官方取值是参考实现的设定，不构成本机硬件与新增控制路径已验证的证明。

当前 G1RA ACTION 协议携带关节角和 kp/kd，但不携带前馈力矩，SDK 桥将 tau 固定为零。若复用该桥，必须明确扩展协议、执行端和验证；优先复用官方手臂控制器完整路径，不能只接入官方 IK 的关节角后宣称与官方链路一致。

已下载并对比机器人上模型，见 [模型对比说明](diagnostics/robot-model-2026-11-05/README.md)：

- 机器人与本机 HoloMotion 标准 URDF 完全相同。
- 官方遥操模型包含灵巧手，每侧约 0.697 kg；HoloMotion 橡胶手约 0.17 kg。
- 当前仿真 XML 与训练 URDF 的躯干合并质量存在约 1.781 kg 差异。

开发前确认实物手部、额外负载、机器人型号版本以及模型一致性。机器人上的 URDF 文件存在，不等于已经针对当前硬件标定。

## 7. 研发阶段与验收

### 阶段 A：离线适配与 IK

完成骨架到目标位姿的转换，不连接电机控制接口。

验收：左右和坐标方向正确；输出有限且在工作空间内；相近输入不会造成关节大跳变；明确观察到手腕朝向和肘形限制；能报告不可达、低置信度及过期数据。

### 阶段 B：MuJoCo 仿真

执行官方 IK 输出及重力补偿，使用明确对应的机器人模型；保留与现有 HoloMotion 仿真的独立入口。

验收：静止与慢速抬臂、前伸、侧举、弯肘连续运行；观察到目标和实测的差异；记录频率和耗时；验证遮挡、断流、不可达目标与暂停恢复。

仿真场景必须明确是固定基座手臂测试，还是存在独立站立控制器的全身测试；不能用固定基座结果宣称自由站立稳定。

### 阶段 C：机器人侧无动作验证

验证模型、依赖、真实关节状态、网络数据与求解时间；不发布电机动作。

验收：能证明官方运控和手臂接口的兼容路径；没有冲突发布者；实际时序满足拟定频率；完整处理数据异常和退出。

### 阶段 D：现场手臂验证

执行前单独取得用户确认。逐步验证保持、小幅单臂、双臂跟随。记录目标角、最终指令角、实测角、前馈力矩及状态；由操作员确认实物效果。

建议首轮测试包含 30 秒人体静止及至少 2 分钟慢速动作，保存峰峰值误差、速度、延迟和异常记录。具体合格阈值根据演示动作和机械条件约定，不预先虚构已达到的精度。

## 8. 当前优先工作：验证 HoloMotion 调整 PD 的效果

本方案暂不启动研发。优先保留当前链路，尝试通过 PD 匹配改善演示效果。

- 仿真默认已恢复模型原 PD，肩肘均约 kp=14.251、kd=0.907；`HOLOMOTION_SIM_PD=model`。
- `bridge` 对比开关会覆盖全身 PD，不是仅修改手臂，不适合用来独立判断肩肘调参效果。
- 后续若继续调参，应保留腿和腰原增益，单独设置肩肘或腕部参数，并记录每次具体改动；该分组调参入口尚待实现。
- 每次比较使用相同初始状态、姿态和动作，区分修改仿真增益、桥配置和实机实际生效的增益。
- 记录 IK 参考、策略目标、最终下发目标和实测角；目标本身乱跳时不能只靠 PD 推断根因。
- CPU 推理是否满足控制周期必须实测，不能把低频或抖动时序的影响全部归为 PD。
- 旧版 8765 服务曾运行在 `/root/dev-original-20261104/...`，不能假定它加载了当前挂载目录的修改；每次实机实验前核对进程工作目录和实际参数。

是否满足演示要求以现场结果为准。本文件不包含任何未经确认的实机启动、控制权切换或自动调参操作。
